# Dedos individuais → ESP8266

Programa separado dos experimentos de Libras e geometria, implementado em
01/11/2026. A câmera reconhece uma mão e identifica cada dedo como um canal:

| ID | Dedo |
|---|---|
| 1 | Indicador |
| 2 | Médio |
| 3 | Anelar |
| 4 | Mindinho |

O polegar é ignorado. Indicador + mindinho é **`[1,4]`**, não o número 2 nem a
soma 5. Indicador + médio + anelar é **`[1,2,3]`**. As 16 combinações, incluindo
nenhum dedo levantado, são representáveis.

## Executar

Feche outro programa que esteja usando a câmera USB e rode na raiz do projeto:

```sh
.venv/bin/hand-esp --camera 1
```

O destino padrão é `http://192.168.0.105`. Mostre uma única mão inteira; a janela
destaca os quatro dedos, o conjunto detectado, o conjunto confirmado e o ACK do
ESP. Mantenha a pose por cerca de 0,2 segundo, além da estabilização individual
dos dedos. **Q/Esc** encerra e tenta enviar estado neutro.

Para escolher a mão direita mesmo quando as duas aparecem:

```sh
.venv/bin/hand-esp --camera 1 --hand right
```

`--hand left` seleciona a esquerda. No padrão `any`, duas mãos visíveis liberam
o estado; o programa não mistura os dedos de pessoas/mãos diferentes. A troca
da mão selecionada reinicia a confirmação. Sem mão, com landmarks inválidos ou
em falha de captura, o alvo de envio fica neutro imediatamente.

Sem enviar nada ao ESP:

```sh
.venv/bin/hand-esp --camera 1 --dry-run
```

Para consultar ou testar a rede sem abrir a câmera:

```sh
.venv/bin/hand-esp --check
.venv/bin/hand-esp --send 1,4
.venv/bin/hand-esp --send 1,2,3
.venv/bin/hand-esp --clear
```

`--send` faz um envio único; o estado expira sem renovação. `--clear` envia
explicitamente o estado neutro. Para outro endereço, use
`--esp http://smarthome-esp8266-01.local`. Se necessário, solicite um modo USB
compatível com `--width 640 --height 480`.

## Entrega e expiração

A transmissão usa uma thread separada do vídeo. Ela mantém apenas o alvo mais
recente, confirma máscara, sequência, mão e lista de dedos no ACK e tenta
novamente após falhas. Mudanças têm intervalo mínimo de 0,25 s; um estado
inalterado é renovado a cada segundo após a confirmação anterior. Não são
enviados frames, landmarks ou imagens, apenas o estado dos quatro canais.

O ESP limpa máscara, mão e rastreamento se ficar **2.500 ms sem um POST válido**.
Isso também cobre queda de rede, encerramento abrupto e falha nativa da câmera.
Ao sair normalmente, o cliente tenta confirmar um POST neutro antes de fechar.
Falta de ACK não é tratada como entrega bem-sucedida.

## Protocolo HTTP · API 1

`GET /health` informa `finger_api: 1` e `finger_lease_ms: 2500`.
`GET /dedos` consulta o último estado e não renova sua validade.

`POST /dedos` usa `application/x-www-form-urlencoded`, sem biblioteca JSON
adicional no firmware. Exemplo para indicador e mindinho:

```http
POST /dedos
Content-Type: application/x-www-form-urlencoded

mascara=9&sequencia=12&rastreando=1&mao=direita
```

```json
{
  "ok": true,
  "mascara": 9,
  "dedos": [1, 4],
  "sequencia": 12,
  "rastreando": true,
  "mao": "direita",
  "recebido": true,
  "expirado": false,
  "idade_ms": 0,
  "lease_ms": 2500
}
```

A máscara usa bits independentes: ID 1 → bit 0, ID 2 → bit 1, ID 3 → bit 2,
ID 4 → bit 3. Portanto `[1,4]` usa máscara 9 e `[1,2,3]` usa máscara 7.
`sequencia` é um inteiro sem sinal de 32 bits, devolvido no ACK. `mao` aceita
`direita`, `esquerda` ou `nenhuma`. Estado neutro exige máscara 0,
`rastreando=0` e `mao=nenhuma`. Mão fechada visível pode ter máscara 0 e
`rastreando=1`. Parâmetros inválidos ou duplicados retornam HTTP 400 sem renovar
o estado. O programa verifica a API antes de abrir a câmera, para distinguir
firmware antigo de falha no reconhecimento.

## Firmware e continuidade com smarthome

O contexto consultado da outra sessão confirmou Wi-Fi/OTA HTTP V3 no NodeMCU
`192.168.0.105`, hostname `smarthome-esp8266-01.local`, com Pi 5 ligado. Essa
versão tinha imagem e `/health`, mas não recebia comandos.

A variante receptora fica em `firmware/finger-receiver/`, neste repositório,
partindo do V3 do projeto `../smarthome`. A versão instalada é
**WIFI OTA HTTP DEDOS LED V5**, com `/dedos` e quatro saídas para LEDs. A imagem em `/`, o
diagnóstico, a configuração de rede e o ArduinoOTA foram preservados.
Os dedos 1–4 acionam os LEDs em D0/D1/D2/D7, respectivamente.
O IR experimental permanece inativo e os pulsos do LED de diagnóstico continuam.

A V5 foi instalada em 02/11/2026 após confirmação da montagem. A configuração
local `leds_config.h` habilita as saídas; o exemplo distribuído continua
desabilitado por padrão. `/health` informa `finger_leds_enabled`, e `/dedos`
inclui `leds_habilitados`, `gpio_leds` e `niveis_gpio` obtidos com `digitalRead`.
Esses níveis não substituem medição com multímetro nem confirmação visual.

### Montagem dos quatro LEDs · confirmada em 02/11/2026

O usuário informou que somente o lado com A0, G, VV, S3/S2/S1/SC/S0/SK,
3V, EN, RST e VIN está acessível na protoboard. Esse lado não fornece quatro
saídas digitais adequadas para este teste. A0 é entrada analógica; os pinos
S estão ligados à interface da flash, e os demais são alimentação/controle.
A referência do [core ESP8266](https://arduino-esp8266.readthedocs.io/en/3.1.2/reference.html#digital-io)
recomenda não usar GPIO6–GPIO11 como I/O nos módulos com flash conectada.

O usuário passou a acessar os pinos digitais e confirmou esta montagem:

| Dedo | LED | Pino NodeMCU | GPIO |
|---|---|---|---|
| 1 · Indicador | 1 | D0 | 16 |
| 2 · Médio | 2 | D1 | 5 |
| 3 · Anelar | 3 | D2 | 4 |
| 4 · Mindinho | 4 | D7 | 13 |

Em 02/11/2026, o usuário informou montagem em D0/D1/D2/D3. Solicitada a
troca de D3 por D7, posteriormente confirmada: D3 é GPIO0 e precisa estar HIGH no
reset para executar a flash. O LED ligado desse pino ao GND pode interferir
nesse nível. [Seleção de boot da Espressif](https://docs.espressif.com/projects/esptool/en/latest/esp8266/advanced-topics/boot-mode-selection.html).
O exemplo reflete D0/D1/D2/D7 e fica desabilitado por padrão. A configuração
local confirmada habilita esses pinos na V5 instalada.

Mapeamento conforme [documentação NodeMCU](https://nodemcu.readthedocs.io/en/release/modules/gpio/).
O usuário confirmou que desconectou o antigo DHT de D2. D5, antes proposto, fica fora deste
mapeamento; seu histórico registra um receptor IR.

Para quatro LEDs comuns visíveis, usar **um resistor de 470 Ω em série com
cada LED**, com esta ligação, feita com USB/alimentação removidos:

```text
GPIO escolhido → resistor → anodo do LED
                           catodo do LED → G/GND
```

Em LEDs novos de duas pernas, a longa normalmente é o ânodo; a curta e o lado
chato do encapsulamento identificam o cátodo. Falta confirmar os resistores
disponíveis e se são LEDs visíveis, em vez dos componentes IR da bancada anterior.

Após confirmar a pinagem, copiar `leds_config.example.h` para `leds_config.h`,
conferir os quatro pinos e habilitar `kFingerLedsEnabled`. O script de build
inclui essa configuração local; a atualização de um receptor já instalado exige
`--force`. **Não habilitar/gravar as saídas antes da confirmação da montagem.**
A implementação prepara saídas inicialmente LOW, aplica um bit por LED e
desliga os quatro em perda de validade, troca de rede ou início de OTA.
Com a configuração desabilitada, não escreve nesses quatro GPIOs.

Ao retomar o firmware no projeto smarthome, incorporar essa rota e os campos
de API no diagnóstico, preservando o OTA. A fonte daquele projeto continua
representando o V3; esta implementação não alterou seus arquivos.

Para reproduzir a compilação com a configuração privada já existente:

```sh
python3 tools/build_finger_receiver.py \
  --secrets ../smarthome/firmware/wifi-ota/secrets.h
```

O script coloca as credenciais e o binário em `.build/`, ignorado pelo Git.
Não incluir esse diretório nem `secrets.h` em commits: o binário também contém
a configuração Wi-Fi. Sem credenciais, a compilação de verificação é:

```sh
arduino-cli compile --fqbn esp8266:esp8266:nodemcuv2 \
  --build-path .build/firmware-check firmware/finger-receiver
```

Upload inicial desta variante por OTA:

```sh
python3 tools/deploy_finger_receiver.py --host 192.168.0.105 \
  --secrets ../smarthome/firmware/wifi-ota/secrets.h
```

A senha OTA é lida em memória, sem passar por argumentos de subprocessos.
O uploader não repete uploads automaticamente e não regrava um receptor API 1
já instalado, exceto quando solicitado com `--force`. Confira `/health` após
qualquer falha antes de tentar novamente. A revisão V4.1 exige exatamente os
quatro campos do protocolo e usa contadores sem limite de oito bits na validação.

## Evidências de 01/11/2026

- 90 testes automatizados passaram; incluem as 16 máscaras, polegar ignorado,
  mão ambígua, perda de rastreamento, confirmação HTTP, renovação, encerramento
  com requisição em andamento e validador C++ compartilhado pelo firmware.
- Arduino CLI 1.5.1, core ESP8266 3.1.2, alvo `esp8266:esp8266:nodemcuv2`:
  firmware compilado e instalado por OTA a partir do Mac. `/health` confirmou
  V4/V4.1, API 1 e OTA ativo após reboot.
- ESP real confirmou as 16 combinações. `[1,4]` retornou máscara 9 e lista
  `[1,4]`; `[1,2,3]` retornou máscara 7. Máscara inválida, estado inconsistente e
  parâmetros duplicados foram rejeitados com HTTP 400.
- Sem renovação, o estado ficou neutro e `expirado=true` após espera de 2,8 s
  (idade observada: 2.957 ms). Imagem HTTP e OTA continuaram disponíveis.
- Teste integrado com a imagem pública `woman_hands.jpg`, MediaPipe 0.10.35 e
  captura simulada de 24 frames: reconhecimento real → estabilidade → HTTP →
  ACK do ESP. Observou-se `[1,2,3,4]` na mão selecionada e estado neutro no fim.
  Não usamos a webcam nesse ensaio; os exemplos `[1,4]` e `[1,2,3]` foram testes
  de transporte, não validação dessas poses em uma pessoa ao vivo.
